# 一、业务方向（10 题）

## B1. 你说医疗问答要"宁可少答，不可答错"，这句话在系统里具体落在哪儿？

**答：**

这句话在我们的系统里不是口号，而是**四个具体的产品行为**：

1. **不答**——检索完全拿不到证据时（图谱为空、文献也为空），系统**不会让模型"凭常识补"**，而是走标准的信息不足话术，建议就医。判断落在 `domain/rules/insufficiency.py::is_insufficient(fact_count, doc_count)`。
2. **降级答**——每条回答都带**依据分级**（`high` / `partial` / `low`，对应 FR-023）。只有结构化知识时是 `high`；含文献是 `partial`；完全没依据或走 direct 通路是 `low`，前端会把"依据不足"作为标签展示出来。
3. **答完再查**——生成之后还有一道**事实护栏**：用**第二次 LLM 调用**核查"答案里的关键陈述能不能在证据里找到"，找不到就在答案末尾追加「（提醒：以上回答中部分内容（xxx）在当前知识库中未找到直接依据，请谨慎参考。）」。它的动作不是**拦下回答**，而是把结论**降级**。
4. **划边界**——涉及诊疗的问题会追加健康风险提示（10.4："以上为一般性健康信息参考，不构成医学诊断……具体用药请咨询执业医师"），并且系统**不诊断、不开方**。

**一句话收口**：我们的"不答"不是拒答，而是"**不把它当作确定结论来答**"——因为医疗信息错的代价，远高于少答的代价。

## B2. 为什么要专门做 18 类固定问答？全部交给大模型自由回答不行吗？

**答：**

因为这 18 类（症状、病因、预防、治疗周期、治疗方式、治愈率、易感人群、并发症、宜吃/忌吃、药品、检查等）是**可以穷举**的信息需求，而它们在图谱里对应的就是**确定的结构化关系**。

> 补充（当前实现）：需求第 9 章的原文是"**至少**支持 18 类"。本项目在此基础上，按需求 14.7「科室数据」又扩展了「疾病→科室 / 科室→疾病」2 类，**当前共 20 类**——它们同样走零 LLM 的模板快路径。

走模板链的好处是三个字：**零 LLM**——

| 优势 | 说明 |
|---|---|
| **便宜** | 一次图谱查询，成本约等于 0 |
| **快** | 毫秒级，链路里没有 LLM 的秒级延迟 |
| **稳** | 结果确定，同一问题两次答案完全一致，**而且不会编** |

反过来，如果全部交给大模型自由回答：慢（每次 1~3 秒）、贵（每问烧 token）、**不稳定**（温度带来随机性 + 幻觉风险），而且还得靠护栏兜底。**把一个"查表就能答"的问题送到 LLM 手里，是纯粹的成本和风险。**

所以我们的分工是：**简单问题走确定性快路径，只有开放问题才动用 LLM**——这也是 FR-024"简单问题不做不必要查询"的原话精神。另外它还是个**降级安全网**：大模型挂了，18 类问答照常工作。

## B3. 用户问"螃蟹不能吃吗"，系统怎么保证"不能吃"这个方向判断是对的？

**答：**

这题的坑在于：**宜忌是"方向敏感"的**。图谱里疾病和食品之间存了**两条语义相反的关系**：

```
(Disease)-[:no_eat]->(Food)      忌吃
(Disease)-[:do_eat]->(Food)      宜吃
```

所以"能不能吃"不是一个查询，而是**先判方向、再选边**，两件事都要做对：

**第一，判方向。** 用户措辞里出现"不能 / 不宜 / 忌 / 禁 / 避免 / 少吃"→ 判 `restrict`；否则 `recommend`。实现是 `domain/rules/diet_rule.py::judge_diet_direction`。

**第二，认实体角色。** 同一句话，"螃蟹不能吃吗"以**食品**为锚点 → 走反向关系 `FOOD_DISEASE_AVOID`（第 13 类）；"感冒不能吃什么"以**疾病**为锚点 → 走正向 `DISEASE_FOOD_AVOID`（第 11 类）。

**最容易错的是第二步。** 如果只按关键词选了一个类型，但实体角色反了，查出来的边就是**相反的关系**——用户问"不能吃"，你答了"宜吃"。这在医学上是**会出事的错**。所以第 10.1 条专门做了"宜忌方向校正"（`adjust_food_qa_type`），关键词命中之后还要再审一次方向。

## B4. "浑身没劲、流鼻涕怎么回事"——图谱里当然查不到，系统该怎么答？

**答：**

这类问题是**口语化的症状描述**，天然不适配图谱。原因是图谱查的是"实体 → 关系 → 实体"，而这句话里根本没有明确的实体-意图配对——连"浑身没劲"能不能识别成症状都两说（词典里大概率没有这个词条）。

**但向量检索恰恰擅长这个**：把整句做语义编码，能找到语义相近的医学文本（比如"感冒的临床表现"这类段落），从而把"这些症状可能指向什么"关联出来。

更完整的做法是**两条路一起上**：

- **图谱侧**：如果能识别出症状实体（比如"流鼻涕"），走 `SYMPTOM_DISEASE`（第 2 类）——反向查"这个症状可能对应哪些疾病"；
- **文献侧**：语义检索拿到相关段落，由模型组织成"可能的解释 + 建议就医"。

这正是我们坚持**混合检索**的原因：**图谱擅长"关系精确"，向量擅长"语义相似"，两者覆盖的是两类不同的信息需求**，不是谁替代谁。而且有一路查空时另一路能兜住——实测中"高血压的非药物治疗措施"这类问题就是靠文献路在起作用。

## B5. 为什么健康 RAG 一定要保留出处？没有出处会怎样？

**答：**

四个理由，从强到弱：

1. **可验证**：用户或医生能**回到原文核对**。医疗场景里"系统说的"不足以成为依据，必须能追到"哪篇文献、第几页"。
2. **可审计**：出了争议能追溯来源、界定责任，而不是一句"模型生成的"。
3. **责任边界**：说清"这条信息来自知识库/文献"，把"信息参考"和"诊疗决策"分开——这是医疗 AI 产品能落地的前提。
4. **可信度线索**：出处本身（期刊、年份、页码）就是权威性的信号，用户据此判断要不要采信。

**没有出处的后果**：用户**无法判断可信度**，也就无法对自己的决策负责；一旦某条信息错了，既查不回来也说不清责任。

我们做到了两层：**摘要级**——每个文献片段都带「来源文件 + 页码」（`RAGAgent.recall()` 拼接时就带上），`Answer.sources` 还按 FR-022 标注来源**类型**（`kg` 结构化 / `lit` 文献）；**展示级**——前端有可折叠的"来源依据"列表，逐条列出，医学文献还能点"查看原文"。

## B6. 系统怎么处理"我真的不知道"？

**答：**

核心设计原则是：**把"不知道"做成一种正常的回答形态，而不是失败。** 三种情形分开处理：

1. **完全没有证据**（召回为空）→ 走标准"信息不足"话术，**不编**。判断是 `is_insufficient(0, 0)`。
2. **有证据但答案没依据** → 护栏核查不通过 → 追加"请谨慎参考"，同时把依据分级降到 `low`。**回答仍然给**，但明确标注不确定性。
3. **检索到了证据，但证据里确实没有这个问题的答案** → 如实说明"资料未包含这部分"，并且**把资料实际覆盖了什么告诉用户**。

第 3 种我们在真实冒烟里碰到过：问"高血压的非药物治疗措施"，检索回来的 5 篇文献全是别的主题（血浆 NRP-1/SOD、尿儿茶酚胺、CGRP 与高血压……），模型的回答是"依据现有资料无法系统回答……上述资料中**未包含**关于高血压非药物治疗的具体内容"，并建议查阅权威指南。

这个回答**质量不高（因为语料没覆盖），但它是对的**——它没有编。这就是"宁可少答"的实际表现。

## B7. 哪些问题系统应该拒绝回答？怎么识别？

**答：**

分三类，处理方式**刻意不同**：

**第一类：非法 / 越权查询 → 硬拦截。**
比如问句里包含写库意图、注入尝试、或诱导系统执行破坏性操作。识别手段是**规则拦截**（`domain/rules/query_guard.py` 的非法模式匹配）+ **Cypher 层校验**（写关键字拒绝、读语句开头白名单）。行为是返回"该请求已被拒绝执行"，**不给任何执行机会**。

**第二类：超出能力边界（确诊 / 开方 / 替代就医）→ 不硬拒，而是"回答 + 风险提示 + 引导就医"。**
这类**不能用拒绝**：一是会伤体验（大量正常问题连带失效），二是责任边界上"如实说明并提醒"比"装作不知道"更负责。所以走的是 10.4 风险提示 + 免责声明。这也正对应面试高频题"医疗场景护栏该拦截还是提醒"——我们选**提醒**。

**第三类：与健康无关（寒暄、闲聊）→ 不检索，直接答。**
走 `direct` 通路：不检索（因为检索也检不出东西），简单回应或引导回健康话题。**这条其实很难做好**，因为它很容易被误判成开放式问题——我们在 `_route` 里专门要求"无实体 + 无类型 + 非开放式"三个条件同时满足才走 `direct`。

## B8. 老年用户问"我血压高，该吃什么药"，系统怎么答才算合适？

**答：**

我把它拆成"**绝对不能做**"和"**可以且应该做**"：

**不能做**：给出具体药名 + 剂量的处方式回答、承诺疗效、替代医生判断。这既是**合规红线**，也是**安全底线**——同一句"血压高"，背后的分级、并发症、肝肾功能完全不同，个体化判断不是问答系统该做的。

**可以做且应该做**：

- 给出**知识库里有的用药方向**（图谱里确实有"疾病 → 推荐药品"的关系，可以说"该疾病在知识库中关联的药物类别包括……"），但**必须**同时说明"具体药物选择、剂量、疗程须由医生根据个体情况决定"；
- 给**用药注意事项**（常见不良反应、不自行加减药、不突然停药）；
- 触发**风险提示**（10.4）与免责声明；
- **明确引导就医**："请到心内科就诊，由医生开具处方"。

语气上同样重要：**不制造恐慌**（不说"你这个很危险"），**也不轻描淡写**——而是"把不确定性说清楚 + 给出下一步行动"。

## B9. 你怎么衡量这个问答系统"好不好"？列出你会用的指标。

**答：**

我分五个维度，并且强调："**每个维度都要有可测量的指标，否则只是感觉**"：

| 维度 | 具体指标 |
|---|---|
| **检索质量** | Recall@k、Top-k 命中率、无关片段占比、图谱召回与文献召回各自的贡献比 |
| **生成质量** | **幻觉率**（无依据陈述占比，对应验收 ACC-020/021）、依据不足率、答案完整度、是否答非所问 |
| **可追溯性** | 来源标注覆盖率、出处正确率（能不能点回去找到） |
| **效率与成本** | 首字时延 / 总时延（P50、P95）、单问 LLM 调用次数、token 成本、缓存命中率 |
| **稳定性** | 各依赖可用性、降级触发率、异常率、超时率 |

**两个我特别想强调的点：**

1. **幻觉率必须人工抽样标注。** 自动指标（比如护栏的"无依据句占比"）只能做辅助——它自己也有误报漏报，不能拿它当唯一真相。
2. **要按问题类型分层统计。** 18 类固定问答的准确率应该接近 100%（本质是查表），而开放式问题天然低；混在一起算平均值没有意义，也看不出问题出在哪一环。

## B10. 如果业务方要求"提高回答率、少说依据不足"，你怎么办？

**答：**

我会先把"回答率"这个词**拆开**——它是症状，不是病。

**可以做的（提质量，顺便提回答率）：**

1. **扩语料**：覆盖不足是"依据不足"的**根本原因**。多进文献与指南，"能答的问题"自然变多，这是最正的路；
2. **提召回**：上 rerank（cross-encoder 精排）、查询改写（把口语问题改写成检索友好的形式）、调融合权重；
3. **降门槛但不降标准**：把"依据不足"的**提示语**改得更有帮助（"资料未覆盖，您可以试着问 XX"），但**事实判断不变**；
4. **区分信息类型**：明确标注"以下为通用健康常识（**非知识库依据**）"，而不是把它混进证据里冒充依据。

**不能做的（要明确拒绝）：**

- 让模型"自由发挥"来凑答案——那是**用幻觉换指标**；
- 把护栏从"提醒"改成"放行且不提"；
- 把"依据不足"的判定放宽（比如把 `low` 也算作"已回答"）。

**我会这么回话术**："回答率低是**症状**不是病。病在语料覆盖和召回质量上，这两块提上去，回答率自然会涨，而且涨得**扎实**。如果靠放宽判定把指标做上去，隐患会整体转移到幻觉率上——医疗场景这条红线动不了。"

# 二、技术方向（10 题）

## T1. ⭐ 稠密检索为什么用 IP（内积）而不是余弦或 L2？归一化和度量必须配套吗？

**答：**

三种度量的区别：

- **L2（欧氏距离）**：`‖a-b‖`，几何距离，**越小越相似**。它受**向量模长**影响——方向相同但模长大的向量，距离也更大；
- **IP（内积）**：`a·b = |a||b|·cosθ`，同时受**方向**和**长度**影响；
- **余弦**：`a·b / (|a||b|) = cosθ`，**只看夹角**，与长度无关。

**关键点：归一化之后，IP 就等于余弦。**

当 embedding 做了 `normalize_embeddings=True`，`|a| = |b| = 1`，于是：

```
a · b = 1 × 1 × cosθ = cosθ
```

所以我们用 IP，拿到的是**余弦语义**，但省掉了余弦那种"每次都要除以模长"的开销——向量库里的 IP 是**原生算子**，更快更省。

**两者必须配套，缺一不可：**

| 情形 | 后果 |
|---|---|
| 只归一化 + 用余弦 | 语义正确，但白白多算一次除法（性能浪费） |
| **只改 IP + 不归一化** | **语义就错了**：模长大的向量会系统性得分偏高（比如长文本向量往往模长更大，会被莫名偏爱） |

我们项目两处都设了：`DENSE_INDEX = {"metric_type": "IP", "index_type": "FLAT"}` + `encode_kwargs={"normalize_embeddings": True}`。

---

## T2. FLAT 和 HNSW 怎么选？你的集合多大，选了什么，为什么？

**答：**

**FLAT（暴力检索）**：拿查询向量跟库里**每一个**向量算距离再排序取 top-k。

- 优点：**召回率 100%**（绝不漏），零参数、零调优；
- 缺点：复杂度 `O(N)`，数据量大时延迟线性增长。

**HNSW（分层可导航小世界图）**：构建多层近邻图，查询时从上层快速跳到目标附近，再在底层精搜。

- 优点：近似对数级复杂度，**快**；
- 缺点：**近似算法会漏召回**，内存开销更大（要存图结构），还有构建成本。

**选型依据是"数据量 + 对召回的容忍度"：**

我们的集合只有 **762 条**切片——这个规模下 FLAT 的查询延迟是毫秒级，实测完全够用。**没有任何理由为了速度牺牲 100% 的召回**，所以选 **FLAT**。

**转折点**：到**百万级**，FLAT 延迟会成为瓶颈，这时换 HNSW，用少量召回率换显著的性能提升。

**加分补充**：真要换，应该**用评测集对比换前换后的 Recall@k 与 P95 时延**再决定，而不是"听说 HNSW 快就换"——因为**召回率下降是隐形的**，用户只会觉得"答案变差了"，很难归因到索引上。

## T3. ⭐⭐ RRF 为什么按"排名"融合而不是按"分数"融合？融合分能用绝对阈值卡吗？

**答：**

**先讲为什么不能按分数融合。** 两路的分数**量纲完全不同**：

- 稠密路是余弦相似度，范围 `[-1, 1]`，0.65 有明确物理含义（夹角约 49°）；
- 稀疏路是 BM25 分，**无上界**——取决于词频、文档长度、语料规模，同一个"12 分"在不同语料下含义都不同。

直接把两路分数加权相加（`0.7×余弦 + 0.3×BM25`），等于把一个 `[-1,1]` 的数和一个可能到几百的数加在一起——**BM25 会完全主导结果，稠密路形同虚设**。

**RRF 的解法是只看排名、不看分数：**

```python
rrf_score[doc] += weight / (rank + c)     # c = 60，rank 从 1 开始
```

它天然规避了量纲问题，因为把"分数"这个不可比的东西**扔掉了**，只保留"排序"这个可比的信号。

**代价（这是我们踩过的坑）：融合分只反映排名，不含相关性信息。**

我在项目里实际算过：权重 `(0.4, 0.6)` 和为 1，`c=60`，所以某片段**在两路都排第 1 名**时，分数也只有：

```
0.6/(1+60) + 0.4/(1+60) = 1/61 ≈ 0.0164
```

**而我们的阈值是 0.65** —— 差了 **40 倍**。所以拿 0.65 去卡融合分，结果是**一条都留不下，检索全空**。

**更隐蔽、也更危险的一点：在融合之前用绝对阈值过滤，会毁掉多路互补。**

举个真实场景：一条片段在稠密路排名靠后（语义不够像），但在稀疏路排第 1（因为"SGLT-2 抑制剂"这种专有名词被 BM25 精确命中）。**融合之后它靠稀疏路的加权爬上来**——这正是混合检索的价值所在。

但如果我在**进融合之前**就用 0.65 把稠密路的低分结果砍掉，就等于**提前杀死了另一路本来能救它的机会**，混合检索直接退化成单路。

**所以我们怎么做：**

- 阈值**只作用于单路稠密检索**（`MilvusVectorStore.search()` 的 `score_threshold`）；
- `HybridRetriever` 融合路**不传**这个参数，让 RRF 自己排序，最后取 top-k 交给生成。

**那"相关性判定"该在哪做？** 三条正路：① 单路各自用自己量纲的阈值（余弦用余弦阈值、BM25 用 BM25 阈值）；② 融合后上 **rerank**（cross-encoder 对"问题+片段"**联合打分**，这才是真正的绝对相关性判定，代价是时延）；③ 取 top-k 交给 LLM，由事实护栏兜底。

## T4. 切片参数 600/100 怎么定的？改成 200/20 会怎样？

**答：**

**先说为什么要切：**

1. 嵌入模型有**输入长度上限**；
2. 更重要的是**检索粒度**——整篇文档一个向量会把语义稀释掉，召回回来的东西"整体相关，但不是你要的那一段"；
3. **上下文预算**——只把最相关的片段给 LLM，省 token、降干扰。

**再说两个参数的权衡：**

| | 切得太大 | 切得太小 |
|---|---|---|
| `chunk_size` | 噪声多、语义被稀释、浪费上下文 token | 语义被切断、上下文缺失 |
| `chunk_overlap` | 冗余多、索引变大 | **句子跨块时语义被截断** |

**overlap 的唯一作用就是防止"语义被切口切断"**：一个完整论证可能横跨两个 chunk，没有重叠的话第二个 chunk 开头就是半句话，检索到了也读不懂。

我们取 **600/100（约 1/6 重叠）**，并用 `RecursiveCharacterTextSplitter` 按分隔符**优先级递归**切：`["\n\n","\n","。","！","？","；","，"," ",""]` —— 尽量落在**段落和句子边界**上，而不是硬砍。

**改成 200/20 会怎样：**

1. **切片数暴涨**（大约 3 倍，762 → 2000+），索引变大、检索变慢；
2. **单块信息量不足**：200 字往往只够说清一个点，模型拿到 8 条也拼不出完整答案，反而**更容易前后矛盾**（不同片段说法不一致）；
3. **段落逻辑被打碎**：比如"1. 病因…2. 症状…"被切进不同块，检索到"2. 症状"那块时完全看不到上文在说什么；
4. overlap 从 100 降到 20，**跨块语义被截断的概率显著上升**。

**诚实补充**：600/100 这个值我们**没做严格的消融实验**去调优，它是在"文档经验值 + 医学文献段落结构"基础上定的。正确做法应该是**用评测集对比几组参数下的 Recall 与答案质量**——这是我认下来的一个改进点。

## T5. ⭐ NL2Cypher 生成的语句，你怎么保证它不会删库、或者拖垮数据库？

**答：**

这是"LLM 直接对接数据库"的必修课。我们的防护是**四层**，从"根本不给你机会"到"给你机会也过不去"：

**第一层：参数化（防注入）。**
实体一律走 `$entity` 参数绑定，**绝不做字符串拼接**。这样用户输入永远只是"值"，不可能改变语句结构。**这是最根本的一层**——这层没做，后面全是补丁。代码在 `services/kg_query_service.py::build_cypher`。

**第二层：规则校验（零成本、先跑）。**
在 `domain/graph/validators.py` 里做四件事：

- **写关键字拒绝**：`CREATE` / `MERGE` / `DELETE` / `SET` / `REMOVE` / `DROP` / `CALL` 等一律拒；
- **读语句开头白名单**：必须以 `MATCH` / `OPTIONAL MATCH` / `WITH` / `UNWIND` / `RETURN` 开头；
- **schema 白名单**：label 与关系名必须落在我们定义的 7 类节点、10 类关系内（既防幻觉出不存在的标签，也防越权读别的数据）；
- **强制补 LIMIT**（`ensure_limit`）：没有 LIMIT 就补一个，防全表扫描。

**第三层：EXPLAIN 预检。**
把语句包成 `EXPLAIN <cypher>` 交给 Neo4j —— 注意这里**只生成执行计划、不执行原查询**。它能验证语法与语义（关系方向对不对、属性存不存在），这是规则校验做不到的。这一步走的是 `GraphStore` 端口，所以**领域层依然不依赖 neo4j SDK**。

**第四层：只读会话（连接层兜底）。**
Neo4j 驱动建会话时指定 `default_access_mode="READ"` —— 哪怕前面三层都被绕过，写操作在**数据库层面**也会失败。

**另外两点**：生成的语句**只进日志，不进用户可见响应**（不暴露内部实现）；整条链路是"生成 → 校验 → 执行 → 格式化"，**任何一步失败都降级，不阻塞问答**。

## T6. 图谱三级递进为什么这么排？顺序能换吗？

**答：**

三级的排列依据是**"成本 × 确定性 × 可用性"**三个维度：

```
① 模板精确查询（QAType 元数据 → 参数化 Cypher）
     成本 0（无 LLM）｜延迟毫秒｜结果确定、不会编
     覆盖：18 类固定问答
        ↓ 查空才往下
② NL2Cypher（LLM 生成 Cypher → 校验 → 执行）
     成本 1 次 LLM 调用｜延迟秒级｜有幻觉风险（靠校验拦）
     覆盖：模板没建模的关系，灵活性高
        ↓ 仍空才往下
③ 规则兜底链（fallback/：词典实体识别 + 规则拼 Cypher）
     成本 0｜延迟毫秒｜结果确定，但覆盖能力弱于 ②
     价值：大模型不可用时的最后通道
```

**顺序不能换，三个理由：**

1. **先用最便宜最确定的**：能查表解决的，绝不多花一次 LLM 调用——这也是 FR-024"简单问题不做不必要查询"的落地；
2. **LLM 放第二位而不是第一位**：LLM 的优势是**覆盖面**（模板没建模的关系它能查），劣势是**成本、延迟、不稳定**。所以它的定位是"模板的补充"，不是主路径；
3. **③ 放最后，因为它是"可用性兜底"而不是"质量优选"**：结果质量低于 ②，只在前两层都拿不到时才用。它真正的价值是**大模型挂了图谱能力不中断**——在无 Key / 离线环境下是唯一通道。

**如果换成 ②→①→③**：等于每问都先花一次 LLM 调用，而 18 类固定问答本来零成本就能答，纯属浪费——成本涨、延迟涨，还引入了本可避免的幻觉风险。

## T7. ⭐ ReAct 的"多跳"具体怎么实现的？步数怎么控制？失败了怎么办？

**答：**

**第一步：循环本身。**
ReAct 是 `思考（Thought）→ 行动（Action，调工具）→ 观察（Observation）→ 再思考` 的循环，由 LLM 决定下一步做什么、什么时候结束。我们用 LangGraph 的 `create_react_agent` 实现，暴露两个工具：`graph_search`（图谱查询）和 `literature_search_tool`（文献检索）。

**第二步：多跳靠"状态累积"。** 这是关键。

LangGraph 用 `add_messages` 这个 **reducer** 把消息**追加**进状态（而不是覆盖），所以每一轮 LLM 看到的是**完整历史**：用户问题 + 历次自己的决策（`tool_calls`）+ 每次工具的返回（`ToolMessage`）。

于是"感冒吃什么药 → 这些药哪个厂家"这种链式查询才能成立：第一轮查出药名列表，第二轮 LLM **基于第一轮的结果**去问第二个问题。这就是固定流水线做不到的地方——**第二步的查询条件在编译期根本不存在**。

**第三步：步数控制。**
`RECURSION_LIMIT`（我们设 10）。**没有上限的话，模型可能陷入"反复调同一个工具"的死循环**——烧钱还不出结果。超限会抛异常，我们捕获后走兜底。

**第四步：失败处理（"Agent 韧性"的核心）：**

- **工具失败不抛异常，返回可读字符串**（比如"未检索到与当前问题相关的文献"）。这样失败被降级成一条"观察结果"，LLM 能看到"这条路不通"，**自主转向**（换另一个工具）或者**诚实承认查不到**；
- **ReAct 整体失败**（超步数 / LLM 异常 / 空回答）→ 回落到 `HybridAgent` 的自动路由（双路召回 + 按意图选路），保证**不空手而归**。

真实轨迹里能看到这个机制在起作用：`search_documents` 返回"未检索到相关文献"，模型于是改用图谱事实作答，并**主动在回答里说明**"本次文献检索未返回相关结果"——这就是"失败当观察"带来的诚实行为。

## T8. ⭐ 为什么护栏要独立成第二次 LLM 调用？为什么温度是 0？

**答：**

**核心原因是"自检偏见"（self-verification bias）。**

如果让模型在**同一轮**里既生成答案、又自查答案，它会有很强的倾向**给自己刚写出来的内容找理由**，而不是真的质疑。原因是这两件事的**目标方向相反**：

- **生成任务**的引力是：把话说完整、说顺、显得有用；
- **核查任务**的引力是：挑刺、怀疑、逐条对证据。

而一次调用里，模型已经"**commit**"了那个答案——后面的"自查"很容易蜕变成**为已有答案辩护**，而不是中立审计。**分开成第二次调用**后，模型面对的是一个干净的任务：*这里有一段声明、一段证据，判断有没有依据*，**没有任何"这是我刚写的、得维护它"的心理包袱**。经验上，同一个模型"查**别人**的答案"远比"查**自己**的答案"可靠。

**温度取 0 的原因**：核查要的是**稳定判定**——同一个输入应该得到同一个结论，而不是每次抽查的结果都不一样。温度 0 让输出尽量确定（贪心解码），也让它更容易严格遵守 JSON 输出格式。

**还有两点一起说**（显出你理解"职责分离"）：

1. **输出格式不同**：生成要自然语言（给人看），核查要结构化 JSON（`{grounded, unsupported, reason}`，给程序用）；
2. **组件可复用**：护栏独立成 `FactGuardrail` 之后，`HybridAgent` 与 `ToolCallingAgent` 共用同一套逻辑，换模型 / 换策略都不用改护栏。

**配套的 fail-open**：护栏自己异常（LLM 挂了、JSON 解析失败）或无参考上下文时，**一律放行**（`grounded=True`）——医疗场景宁可漏检，也不能因为"体检失败"而中断服务。

## T9. ⭐ 你说 147 个测试用例"全离线"，怎么做到的？架构上做了什么保证？

**答：**

这不是"写测试时特意避开网络"，而是**架构本身保证**了这件事。

**根因是端口-适配器（依赖倒置）：**

```
domain/ports.py            ← 领域自己定义抽象（Protocol）
    LLM / GraphStore / LiteratureSearch / CacheStore / EntityRecognizer

infrastructure/            ← 基础设施反向实现这些抽象
    OpenAILlm / Neo4jGraph / MilvusVectorStore / RedisManager / MedicalDictionary
```

因为领域层**只依赖端口、不 import 任何 SDK**，测试就可以注入**替身**：`tests/conftest.py` 提供 `FakeLLM` / `FakeGraph` / `FakeRecognizer` / `FakeLiterature`，于是 `IntentService(llm=FakeLLM(...), recognizer=FakeRecognizer(...))` 就能**完全离线**跑通业务逻辑。

**还有两道"守住架构"的测试：**

1. `test_architecture.py`：用 **AST 静态分析**检查依赖方向——domain 不得 import 任何外层、application 里只有组合根 `runtime.py` 能 import infrastructure、fallback 不得 import application / interfaces、interfaces 不得直接碰数据资源。**一旦有人加了反向 import，测试立刻失败**；
2. `test_ports.py`：用 `isinstance`（`@runtime_checkable`）做**结构一致性检查**——因为 Protocol 是结构化类型，Python 不会在实例化时报错，只能靠测试保证"替身真的满足契约"。

**收益：**

- **秒级反馈**（147 个用例本地 7 秒跑完）；
- **CI 不需要起任何外部服务**（不要 Neo4j / Milvus / Redis / API Key），成本极低，也不会因为"测试环境数据库没起来"而误报；
- 可以直接在**无网、无 Docker** 的机器上完整回归。

**但我必须说清边界**：离线测试覆盖的是**逻辑**，不覆盖**真实依赖的集成**。所以我还做了**真实冒烟**（起真实 Neo4j + Milvus + DeepSeek 跑端到端），以及一次针对护栏的**实证**（用文档里的例子验证它真的会判 `grounded: false`）。**单元测试与真实冒烟是互补的**，不能说"我有 147 个离线测试"就万事大吉。

## T10. 如果并发到 100 QPS，这套系统哪里最先崩？怎么优化？

**答：**

**结论先说：最先崩的一定是 LLM，不可能是数据库。**

理由：我们每问至少要 **1 次生成 + 1 次护栏**（`agent` 模式更多），这两次都是**秒级延迟、有速率限制、还按 token 计费**的外部调用。而 Neo4j / Milvus 是本地服务、毫秒级、可水平扩展——**瓶颈必然在上游模型**。

**优化按"先保命、再提吞吐"的顺序：**

**1. 保命层（防止被打挂）**

- **缓存**：相同问题直接命中 Redis（已实现），并带**幂等锁**防击穿（同一问题并发只让一个去算，其余等结果）；
- **限流 + 排队 + 熔断**：超出 LLM 承载能力就排队或直接返回"稍后重试"。**打爆上游比部分失败更糟**——全部超时等于全挂；
- **降级开关**：护栏可关（省一次调用）、`agent` 模式超步数回落固定流水线、检索路不可用降级为单路。

**2. 提效层（减少不必要的 LLM 调用）**——**性价比最高**

- **能用模板/规则答的绝不走 LLM**。我们的 18 类固定问答就是零 LLM 的，这类问题占比越高，实际 LLM 压力越小；
- 利用 **prompt caching**（很多模型支持前缀缓存），省钱省时延。

**3. 扩展层**

- **异步化**：FastAPI 端点改 `async`，把 Neo4j / Milvus / LLM 调用都异步化——否则线程池会被阻塞式 IO 占满，并发上不去；
- **连接池**：Neo4j driver / Milvus client 复用连接；
- **拆分模型**：护栏可以用更小更便宜的模型（它只需要判"有没有依据"），把贵的模型留给生成。

**一句话总结**：**先保证不被打挂（缓存 + 限流 + 降级），再谈提升吞吐（异步 + 减少调用 + 连接复用）。**

# 附：回答时的三条心法

1. **业务题**：**原则 → 落地手段 → 边界**。
   例：宁可少答（原则）→ 四种产品行为（落地）→ 不诊断不开方（边界）。

2. **技术题**：**机制 → 为什么这么选 → 代价是什么**。
   例：RRF 只看排名（机制）→ 规避量纲问题（为什么）→ 融合分不含相关性、不能卡阈值（代价）。

3. **每题挂一个具体数字或真实案例**。
   有效数字：`762 条切片`、`8808 条疾病记录`、`7 类节点 / 10 类关系`、`c=60 / 融合分上限 0.0164`、`阈值 0.65`、`chunk 600/100`、`147 个离线用例`、`18 类固定问答`、`RECURSION_LIMIT=10`。
   真实案例：实测"高血压非药物治疗"因语料未覆盖而**如实回答依据不足**；`search_documents` 返回空后模型**改用图谱并主动说明**。

> 有数字和案例，和"只会背概念"的人的区别会立刻显现出来。
