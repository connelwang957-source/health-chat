# 一、本项目相关面试题

## 11.1.1 RAG（检索增强生成）

### Q1. RAG 的基本流程？为什么它能缓解大模型幻觉？

**三段式：召回（Retrieve）→ 拼接（Augment）→ 生成（Generate）。**

1. **召回**：把用户问题向量化，去知识库检索最相关的若干片段；
2. **拼接**：把片段塞进提示词的上下文（本项目是 `<context>` 与 `<graph_facts>` 两个槽位）；
3. **生成**：让大模型**基于这些材料**组织回答。

**为什么能缓解幻觉**：大模型的答案来自**参数记忆**（不确定、不可追溯、可能过时）；
RAG 把**外部证据**放进上下文，把"开放生成"变成"**有约束的摘录 + 组织**"，
并且证据**可追溯**（本项目每段都带「来源文件 + 页码」），用户能回原文核验。
即"**有据可依**"取代"**模型记忆**"。

**但是值得注意的是**，RAG技术不能彻底消除LLM的幻觉，因为LLM的逐个输出本质是概率的结果，因此RAG技术也只能对其做约束缓解幻觉现象，

---

### Q2. 召回质量怎么保证？召回到无关文档有什么后果？

*本项目采用以下手段：**

| 手段 | 做法 |
|---|---|
| 相关性阈值过滤 | `SEARCH_SCORE_THRESHOLD=0.65`（稠密路余弦），低于阈值直接丢弃 |
| 混合检索 | 稠密 + 稀疏 → RRF 融合，互补提升召回（见 Q4） |
| top-k 控制 | `RETRIEVAL_TOP_K=8`，只把最相关的若干条给模型 |
| 切片质量 | `CHUNK_SIZE=600 / CHUNK_OVERLAP=100`，尽量在语义边界切 |

**召回到无关文档的后果**：污染上下文 → 模型被误导答非所问；医疗场景更危险（可能给出错误医学结论）。本项目的取舍是"**宁可少答，不可答错**" —— 宁可不召回，也不要召回噪声。

---

### Q3. 为什么要对文档切片（chunking）？chunk_size / overlap 怎么权衡？

**为什么切：**

1. 嵌入模型有**输入长度上限**，长文必须切；
2. **检索粒度**问题：整篇文档一个向量会把语义**稀释**，召回不准；
3. **上下文预算**：只把最相关的片段给 LLM，省 token、降干扰。

**怎么权衡：**

| 参数 | 太大 | 太小 |
|---|---|---|
| chunk_size | 噪声多、语义稀释、浪费 token | 语义被切断、上文缺失、答不完整 |
| overlap | 冗余多、库变大 | 句子跨块时**语义被切断** |

所以 `overlap` 的作用就是**防止语义在切口处被截断**。经验值是 chunk 的 10%~20%。

**本项目**：`CHUNK_SIZE=600`、`CHUNK_OVERLAP=100`（约 1/6），
用 `RecursiveCharacterTextSplitter`，分隔符按优先级递归尝试：
`["\n\n","\n","。","！","？","；","，"," ",""]` —— **尽量在段落/句子边界断开**。

---

### Q4. 混合检索里 dense 和 sparse 分别解决什么问题？

| | dense（稠密向量） | sparse（BM25 稀疏） |
|---|---|---|
| 机制 | 语义相似度（向量距离） | 关键词字面匹配（词频 + 逆文档频率 + 长度归一化） |
| 擅长 | **同义、口语化、模糊表达**（"浑身没劲" ↔ "乏力"） | **药名、编号、专有名词、缩写**（"SGLT-2 抑制剂"、"NRP-1"、"第3页"） |
| 短板 | 专有名词/罕见词易漂移 | 换个说法就匹配不到 |

**两者互补**：dense 抓"意思像"，sparse 抓"字面中"。

**融合用 RRF（Reciprocal Rank Fusion）**：按**排名**融合而不是按分数融合 ——
因为两路的分数**量纲不同**（余弦 vs BM25 分）无法直接相加。

**本项目**：`domain/rag/vectorstore.py::HybridRetriever`，权重 `(0.6, 0.4)`（稠密、稀疏），
用 `EnsembleRetriever` 做 RRF；任一路不可用则**自动降级为单路**，不阻断问答。

## 11.1.2 向量数据库 & Embedding（Milvus + BGE-M3）

### Q1. IP / 余弦 / L2 三种相似度度量的区别？为什么归一化后 IP 等价余弦？

- **L2（欧氏距离）**：几何距离，**越小越相似**；
- **IP（内积）**：`a·b`，同时受**方向**和**长度**影响；
- **余弦**：`a·b / (|a||b|)`，只看向量**夹角**（方向），与长度无关。

**归一化后 |a| = |b| = 1，于是 `a·b = cos(a,b)`** ——
所以可以用**计算更便宜的内积**，得到**语义上更好的余弦相似度**。

---

### Q2. FLAT 和 HNSW 的权衡？

| | FLAT（平坦索引，暴力检索） | HNSW（分层可导航小世界图） |
|---|---|---|
| 召回率 | **100%**（与全量算距离） | 近似，**可能漏召回** |
| 速度 | O(N)，数据量大时慢 | 近似对数级，**快** |
| 内存 | 低（只存原始向量） | 高（要存图结构） |

**选型阈值**：数据量小（万级以下）→ FLAT 足够且精确；
到**百万级**、FLAT 查询延迟成瓶颈 → 换 HNSW，用少量召回率换速度。

**本项目**：集合仅 762 条切片 → 选 **FLAT**（精确、零调参）。

---

### Q3. 为什么 hybrid 融合分数不能直接用绝对阈值过滤？

**这是本项目实际踩过的坑。**

- **dense 的余弦分**是**绝对相似度**：0.65 有明确物理含义（夹角约 49°）；
- **RRF 融合分**是**逐查询归一化后的的相对排名分**（约 [0,1]）：它的含义是"在这条查询里排第几"，**换一条查询就不可比**。

dense的结果值一般在［－１，１］，ｓｐａｒｓｅ的结果指一般不固定要取决于查询词语料规模和文档强度，因此两者**量纲与语义都不同**。用 0.65 去卡融合分，会把**本来正确但相对排名靠后**的片段误杀，

**正确做法**：阈值只作用于**单路检索的绝对分**；融合环节让 RRF 自己决定排序。

---

### Q4. BGE-M3 的 dense + sparse 双通道设计解决什么问题？

BGE-M3 是"**一个模型同时输出 **dense 稠密向量** + **sparse 稀疏权重**两种

**解决的问题：**
1. **一次推理得到两路表示** → 省一次编码、延迟更低；
2. **两路口径统一**（同一模型同一空间），比"embedding 模型 + BM25 统计"这种**两套机制**更协调；
3. 稀疏权重是**学出来的**，比纯统计的 BM25 更能抓领域关键词。

## 11.1.3 知识图谱 & NL2Cypher（Neo4j）

### Q1. NL2Cypher 完整流程？为什么必须"生成 → 校验 → 执行"，而不是生成完直接执行？

**四步：生成（LLM）→ 校验（规则 + EXPLAIN）→ 执行（参数化只读）→ 格式化。**

**为什么必须校验：因为 LLM 生成的 Cypher 不可信。** 它可能：

- 语法错、引用了图谱里不存在的 label / 关系名；
- **更危险：生成写操作**（`CREATE` / `MERGE` / `SET` / `DELETE` / `DROP`）—— 直接执行可能删库；
- 生成无 `LIMIT` 的全表扫描或笛卡尔积，**拖垮数据库**。

**双层校验（本项目 `domain/graph/validators.py`）：**

1. **规则层**（零成本、先跑）：
   - 必须以读语句开头（`MATCH` / `OPTIONAL MATCH` / `WITH` / `UNWIND` / `RETURN`）；
   - **拒绝写关键字**（`CREATE`/`MERGE`/`DELETE`/`SET`/`REMOVE`/`DROP`/`CALL`…）；
   - label / 关系名对照 **schema 白名单**；
   - **强制补 `LIMIT`**（`ensure_limit`）。
2. **EXPLAIN 层**：把 `EXPLAIN <cypher>` 交给 Neo4j —— **只生成执行计划、不执行原查询**，
   用来验证语法与语义。

---

### Q2. 让 LLM 生成 Cypher 有哪些安全风险？如何防注入？

**风险四类：**

1. **破坏性语句**：`DROP`/`DELETE` → 数据被删；
2. **越权读取**：读不该读的标签或属性；
3. **注入**：用户输入被**字符串拼接**进语句（`"...WHERE d.name='$user_input'"` 这种）；
4. **性能攻击**：无 LIMIT 的笛卡尔积。

**防护（本项目逐条落实）：**

| 风险 | 对策 | 落在哪 |
|---|---|---|
| 注入 | **参数化**，实体一律走 `$entity`，**绝不字符串拼接** | `services/kg_query_service.py::build_cypher` |
| 破坏性 | **只读会话** `default_access_mode="READ"` + 写关键字拒绝 | `infrastructure/graph.py`、`validators.py` |
| 越权 | 读语句开头白名单 + **schema 白名单**校验 label/关系 | `validators.py` |
| 性能 | **强制 LIMIT** + `EXPLAIN` 预检 | `ensure_limit`、`CypherValidator` |

另外：**LLM 生成的语句只进日志，不进入用户可见响应**（防止暴露内部实现）。

---

### Q3. 知识图谱 vs 向量检索，各自适合什么查询？

| | 知识图谱（Neo4j） | 向量检索（Milvus） |
|---|---|---|
| 适合 | **精确关系、多跳、结构化事实** | **模糊语义、长文本、同义表达** |
| 例子 | "感冒有哪些症状"（`Disease-[:has_symptom]->Symptom`）、"阿莫西林治哪些病"、多跳"药品→厂商" | "浑身没劲、流鼻涕怎么回事"、"XX 治疗的新进展" |
| 答案形态 | 确定的实体-关系-值 | 相关段落（需要再组织） |
| 弱点 | 口语化提问匹配不上；关系没建模就查不到 | 精确关系和计数不擅长 |

**本项目两条都保留**，由 `HybridAgent._route()` 按问题自动选（FR-024）：
命中 18 类固定问答 → **KG**；开放式 → **RAG / 双路**。

## 11.1.4 Agent / ReAct / 工具调用（LangGraph + LangChain）

### Q1. 什么是 ReAct？和固定流水线（普通 RAG）的本质区别？

**ReAct = Reason + Act**：`思考 → 行动（调工具）→ 观察 → 再思考 …` 的循环，直到给出答案。

**本质区别：控制权在谁手里。**

| | 固定流水线 | ReAct |
|---|---|---|
| 谁决定"查不查/查哪个/查几次" | **开发者**（写死的 if/else） | **LLM 自己** |
| 多跳能力 | ❌ 做不了链式依赖 | ✅ 第二步能用第一步的结果 |
| 可预测性 | 高（流程固定） | 低（模型即兴），所以要有**步数上限** |

**本项目**：`application/tool_agent.py::ToolCallingAgent`，
用 LangGraph 的 `create_react_agent`，暴露两个工具
`graph_search`（图谱）与 `literature_search_tool`（文献），步数上限 `RECURSION_LIMIT=10`。
简单问候（"你好"）可能**一次工具都不调**直接作答 —— 这正是固定双路做不到的。

---

### Q2. LangGraph 的核心概念？`add_messages` reducer 在多跳里起什么作用？

**三大机制：**

1. **State（状态）**：图共享的状态对象；字段用 **reducer** 定义"如何合并更新"；
2. **Node + Edge（节点与边）**：节点是函数（读 State → 返回要更新的字段）；边决定流向，
   **条件边**按状态动态选路；
3. **Checkpoint / 中断恢复**：状态可存档 → 支持人机协作、断点续跑、多轮记忆。

**`add_messages` 是什么**：它指定"这个字段是消息列表，更新时**追加（append）**而不是覆盖"。

**在多跳里的作用**：让**下一轮能看到全部历史** —— 用户问题 + 历次的 AI 决策
（`tool_calls`）+ 每次工具的返回（`ToolMessage`）。
这正是 ReAct 能"边看边推理"的前提：模型不是每轮从零开始，而是**在完整轨迹上继续决策**。

---

### Q3. 为什么工具调用 Agent 用低温（0.2）？

**因为工具调用是"结构化决策"，动作正确性 > 文采多样性。**

- 温度高 → 容易**乱调工具、编造工具名、参数胡填**（hallucinated tool call）；
- 温度低 → 输出更确定、更贴 schema，工具选择与参数填写更稳。

**同一条原则在别处的体现**（能说出来很加分）：

| 环节 | 温度 | 原因 |
|---|---|---|
| NL2Cypher 生成语句 | **0.1** | 要的是**合法**的 Cypher，不是好文采 |
| ReAct 决策 | 低 | 动作要正确 |
| 融合生成（给人看） | 0.3~0.7 | 这里才需要表达流畅 |
| **事实护栏核查** | **0.0** | 要**稳定判定**，不要随机性 |

---

### Q4. 为什么工具返回"可读字符串"而不是抛异常？

**这是"Agent 韧性"的设计。**

- 如果工具**抛异常** → 整个 ReAct 循环崩掉 → 用户看到报错，什么也得不到；
- 如果工具**返回可读文本** → 失败被降级成一条"**观察结果**"，LLM 能看到
  "这条路不通"，于是**自主转向**（换另一个工具）或**诚实承认查不到**。

即：**把失败当作信息，而不是当作中断。**

**本项目的印证**：`application/tools.py` 的两个工具都返回字符串；
实际轨迹里 `search_documents` 返回"未检索到与当前问题相关的文献"，
模型于是**改用图谱事实作答**，并在回答里**主动说明**"本次文献检索未返回相关结果" ——
这就是"失败当观察"带来的诚实行为。

## 11.1.5 防幻觉 / 事实护栏

### Q1. 为什么护栏要独立成第二次 LLM 调用，而不是第一次生成时让模型自查？

**核心原因：自检偏见（self-verification bias）。**

当模型在**同一轮**里既当"答题者"又当"裁判"，它倾向于**给自己刚写出来的答案找理由**，
而不是真的去质疑。两个任务的**目标恰好相反**：

- 生成任务的引力：把话说完整、说顺、显得有用；
- 核查任务的引力：挑刺、怀疑、逐条对证据。

一次调用里，模型已经"**commit**"了答案 → 后面的"自查"很容易变成**辩护**，
而不是中立审计。**分开调用后**，模型面对的是干净的任务：*一段声明 + 一段证据，判断有无依据*，
**没有"这是我刚写的，得维护它"的心理包袱**。经验上，同模型"查**别人**的答案"远比"查**自己**的答案"可靠。

**另外三点收益（一起答，显得完整）：**

1. **参数不同**：生成要发散（温度高）、核查要确定（温度 0）；
2. **输出格式不同**：生成是自然语言，核查是结构化 JSON（`grounded`/`unsupported`/`reason`）；
3. **职责分离 → 可复用**：护栏是独立组件，`HybridAgent` 与 `ToolCallingAgent` 共用。

> 代码：`domain/guardrail/fact_guardrail.py::FactGuardrail`

---

### Q2. 护栏"降级放行"（fail-open）的设计考量？

**这是"可用性 vs 安全"的权衡：护栏本身不该成为新的故障点。**

哪些情况 fail-open（放行）：

- **无参考上下文**（如 `direct` 通路没检索）→ 没有可比对的证据，跳过核查；
- **LLM 调用失败 / JSON 解析失败** → 记为"核查失败，跳过"。

**为什么**：

1. 医疗场景要**保证有回答**（哪怕标注为"需谨慎参考"），不能因为一次核查失败就整条不可用；
2. 护栏是**额外保险**，不是单点依赖 —— 它的价值是"多抓一个错"，不是"拦住所有回答"。

**配套设计**：`GUARDRAIL_ENABLED` 可整体关闭（关掉能省一次 LLM 调用）。

**并且本项目选"提醒不拦截"**：无依据时**在答案末尾追加**
「（提醒：以上回答中部分内容（xxx）在当前知识库中未找到直接依据，请谨慎参考。）」，
**而不是撤下回答** —— 责任边界更清楚：告诉用户"哪部分没依据"，让他自己判断。

## 11.1.6 缓存（Redis）

### Q1. 缓存穿透 / 击穿 / 雪崩分别是什么？怎么解决？

| 问题 | 含义 | 解法 |
|---|---|---|
| **穿透** | 查**根本不存在**的数据，缓存永远不命中，每次都打到数据库 | **负缓存**（把空结果也缓存一小段时间）、**布隆过滤器**、参数校验前置 |
| **击穿** | 某个**热点 key 突然过期**，瞬间大量并发请求同时打到数据库 | **分布式锁**（只让一个请求去重建，其余等待/返回旧值）、逻辑过期 |
| **雪崩** | 大量 key **在同一时刻集中过期**，数据库瞬间被打爆 | **TTL 加随机抖动**（错开过期时间）、多级缓存、限流降级 |

**本项目**：`infrastructure/cache.py::RedisManager`
（`get_json` / `set_json` / `acquire_lock`（SETNX 幂等锁）/ `release_lock`）
+ `domain/services/cache_service.py`（问题规范化 → 生成 key，`try_lock` 抢锁后才计算）。

**还有一条韧性设计**：Redis 连不上时 `available=False`，**问答照常进行**，只是没了秒回。

---

### Q2. 为什么缓存 key 用 MD5？

**三个理由：**

1. **防大 key**：用户问题可能很长（本项目限 500 字），散列后变成**定长**字符串；
2. **固定长度**：便于统计与管理；
3. **避免特殊字符**：中文、空格、换行、标点在 key 里容易出问题。

**本项目实际用 SHA-256**（理由完全相同，且抗碰撞更强）：

```python
cache_key = "kb:ans:" + sha256(f"{mode}::{normalize_question(question)}")
```

细节两个：统一 `kb:` 前缀（便于批量清理/统计）；问题先**规范化**
（NFKC + 小写 + 去标点空白）→ 同一问题的不同写法**命中同一个 key**。

## 11.1.7 架构 / DDD / 端口适配器

### Q1. 领域驱动架构是什么？依赖倒置怎么体现？

**DDD 分层的核心思想**：复杂度在**领域规则**上，而技术细节（数据库、LLM、缓存）
应当被隔离在外层，让领域逻辑**独立于框架存在、可被纯代码测试**。

**依赖倒置（DIP）的体现 —— 反转的是"谁依赖谁"：**

```python
# domain/ports.py —— 领域**自己定义**抽象（不 import 任何 SDK）
class LLM(Protocol):
    def complete(self, system: str, user: str, ...) -> str: ...

# infrastructure/llm.py —— 基础设施**反向实现**它
class OpenAILlm(LLM): ...

# application/runtime.py —— 组合根把两者接起来
def get_intent_service() -> IntentService:
    return IntentService(get_llm(), get_dictionary())
```

依赖箭头从「领域 → 具体 SDK」**倒置**为「具体 SDK → 领域」。
于是领域层**不 import 任何 SDK** → 可以**完全离线单测**
（本项目 147 个用例不连 Neo4j / Milvus / LLM，靠 `tests/conftest.py` 的替身注入）。

**三条硬规则（由 `tests/test_architecture.py` 用 AST 静态固化）：**

1. `domain` **不得** import 任何外层（infrastructure / application / interfaces / fallback）；
2. `application` 里**只有 `runtime.py`**（组合根）可 import infrastructure；
3. **数据/资源归领域层所有**，`interfaces` 不得直接读写文件/向量库。

---

### Q2. Protocol 和 ABC + @abstractmethod 的区别？

| | `Protocol` | `ABC + @abstractmethod` |
|---|---|---|
| 类型系统 | **结构化类型**（鸭子类型）：只要"有这些方法"就算实现 | **名义类型**：必须显式继承 |
| 强制继承 | ❌ 不强制 | ✅ 强制 |
| 实例化时检查 | ❌ Python 不报错 | ✅ 抽象方法未实现会报错 |
| 适合 | 包装第三方 SDK 的**薄适配器**（不必改动继承链） | 自己的类体系，需要强约束 |

**代价**：`Protocol` 的契约**只能靠约定和测试保证** ——
所以本项目用 `@runtime_checkable` + `tests/test_ports.py`（`isinstance` 结构检查）来兜底。

---

### Q3. 领域层和应用层的职责边界？

**分水岭不是"步骤多不多"，而是：这段逻辑是"稳定可复用的业务能力"，还是"某个产品的一次性编排"。**

| | 领域层 domain | 应用层 application |
|---|---|---|
| 放什么 | 业务规则、可复用能力 | 用例编排（"先做什么、失败怎么办"） |
| 本项目例子 | `NL2Cypher`（生成→校验→执行→格式化）、`FactGuardrail`、`vectorstore`、`rules/`（第 10 章纯函数） | `HybridAgent`（选路 + 融合 + 兜底）、`NL2CypherAgent`（主路径 + 兜底）、`ToolCallingAgent`（ReAct 循环） |

**最典型的对照**：`NL2Cypher`（domain，被**三个 Agent 复用**）
vs `NL2CypherAgent`（application，只负责"主路径 + 兜底"这一个**产品决策**）。

**一句话判断法**：*哪天你想在 domain 里写"先查图谱再查向量"这种 if-else 流程，
就是在往 domain 塞编排，要拉回 application。*

**补充：六边形架构（Ports & Adapters）** —— 本项目就是它的一个实例：
"端口"是领域需要的抽象能力，"适配器"是外层的具体实现（Neo4j / Milvus / DeepSeek / Redis）。

**本项目用了三种架构范式**：分层（领域）架构 + Clean 架构（依赖倒置）+ **ReAct**（Agent 范式）。

## 11.1.8 业务方向（大健康 AI）

### Q1. 健康问答相比通用问答，最核心的额外要求是什么？

**四个词：事实性、可追溯性、防幻觉、安全。**

1. **事实性**：医学信息错了会**伤人**，不能"大概对"——所以优先用结构化知识（图谱）给确定答案；
2. **可追溯性**：每条信息都要有出处（来源文件 + 页码），可核验、可审计；
3. **防幻觉**：**宁可少答，不能答错**——依据不足就明说"依据不足"，并加事实护栏二次核查；
4. **安全**：不诊断、不开方、不替代医生；涉及诊疗给**风险提示 + 免责声明**。

---

### Q2. 为什么健康 RAG 要保留出处（source + page）？

1. **可追溯 / 可审计**：用户或医生能回到原文核对，而不是"系统说的"；
2. **责任边界**：明确"依据来自哪里"，把"信息参考"与"诊疗决策"分开；
3. **可信度判断**：出处（期刊、年份、页码）本身是权威性线索。

**本项目**：`RAGAgent.recall()` 拼上下文时每段都带「来源文件 + 页码」；
`Answer.sources` 按 FR-022 **标注来源类型**（`kg` 结构化知识 / `lit` 医学文献）；
前端"来源依据"可折叠列表逐条展示。

---

### Q3. 多跳医疗查询（"感冒吃什么药 → 这些药哪个厂家"）为什么固定流水线做不了？

**因为它是链式依赖：第二步的输入 = 第一步的输出，而第一步的结果运行时才知道。**

固定流水线要表达它，只能写死"先查 A 再查 B"，
但 B 的查询条件 —— **具体是哪些药** —— 在**编译期根本不存在**。
换句话说：**流程的"形状"取决于数据**，写死的流程表达不了。

只有 ReAct 的"**查 → 看 → 再查**"能表达：
LLM 拿到第一步的工具结果，据此**改写**第二步的查询（药名列表 → 逐个查厂商）。

**本项目**：`ToolCallingAgent`（`RECURSION_LIMIT=10` 限制步数，防止无限循环）。

---

### Q4. 医疗场景的护栏应该"拦截"还是"提醒"？为什么？

**本项目选择"追加提醒、不拦截"。**

理由三条：

1. **医疗责任边界**：系统定位是"健康信息参考"，不是诊疗决策。把不确定性**如实标注**
   比"装作什么都不知道"更负责，也更接近真实使用场景；
2. **可用性**：护栏是 LLM 判定，**存在假阳性**。如果一律拦截，很多正常问题也答不了；
3. **"宁可不答不能答错"的正解**：这里的"不答"不是"拒答"，而是
   "**不把它当作确定结论来答**" —— 用提醒把结论**降级**为"需谨慎参考"。

**配套**：护栏自身异常时 **fail-open**（绝不因为检查失败而中断服务）。

### 2. CICD 是什么意思

**CI（Continuous Integration，持续集成）+ CD（Continuous Delivery/Deployment，持续交付/部署）。**

- **CI**：频繁把代码合并到主干，每次合并**自动**构建 + 跑测试，尽早发现集成问题；
- **CD**：CI 通过后**自动**交付到测试/生产环境（Delivery = 可随时发布；Deployment = 自动发布）。

**价值**：把"集成、测试、发布"从人工变成流水线 → 缩短发布周期、降低人为失误。

**工具**：GitHub Actions / GitLab CI / Jenkins。

**本项目很适配 CI**：`pytest tests/ -q` **147 个用例全部离线**
（不连 Neo4j / Milvus / LLM，用替身注入）→ 流水线里不需要起任何外部服务。

### 3. RAG 的完整链路

```
【离线建库】
文档采集 → 清洗解析(OCR/PDF) → 切片(chunk) → 向量化(embedding)
        → 写入向量库（+ 可选导出关键词索引/BM25 语料）

【在线问答】
用户问题 → (可选：查询改写/意图识别)
        → 检索：稠密 / 稀疏 / 混合(RRF 融合) → (可选：重排 rerank)
        → 拼接上下文（带出处：来源文件 + 页码）
        → LLM 生成
        → (可选：事实护栏核查) → 输出 + 来源列表
```

意图分类 → 自动选路 → 双路召回（图谱三层递进 + 文献稠密/稀疏）→ 融合生成
→ 依据分级 → **事实护栏** → 组装 `Answer`（正文 + 来源 + 可靠性 + 风险提示）。

### 4. Function Calling 与 Tool Calling 的区别

| | Function Calling | Tool Calling |
|---|---|---|
| 是什么 | 模型厂商提供的**底层能力**：模型输出结构化的"函数名 + 参数(JSON)" | 更上层的**框架抽象**（如 LangChain `@tool`） |
| 谁执行 | **开发者**拿到 JSON 后自己执行，再把结果回传 | 框架负责 schema 生成、调用分发、结果回灌 |
| 范围 | 通常是"函数" | 可以是函数、API、检索器、数据库查询…… |

**关系**：Tool Calling **通常基于** Function Calling 实现。

**本项目**：`application/tools.py` 用 LangChain `@tool` 把
"图谱查询 / 文献检索"封装成两个工具，交给 `create_react_agent` 自主调用。

### 5. LangGraph 三大机制

1. **State（状态）+ Reducer**：图共享状态；用 reducer 定义字段如何更新
   （如 `add_messages` = 追加消息而非覆盖）；
2. **Node + Edge（节点与条件边）**：节点是函数（读状态 → 返回更新），
   条件边按状态**动态选路** —— 这就是"循环"和"分支"的实现方式；
3. **Checkpoint（持久化 / 中断恢复）**：状态可存档 → 支持
   **human-in-the-loop**（人在环中审批）、断点续跑、多轮记忆。

**本项目用到 1、2**：`create_react_agent` 内部就是
"消息状态（`add_messages`）+ 工具节点 + 条件边（有 `tool_calls` 就去执行工具，否则结束）"。

### 7. Redis 和 MySQL 的区别，各自的数据贮存在什么位置

| | Redis | MySQL |
|---|---|---|
| 类型 | **内存**键值数据库（可持久化） | **磁盘**关系型数据库 |
| **数据位置** | **内存**为主；持久化落盘（RDB 快照 / AOF 追加日志） | **磁盘**：InnoDB 表空间 `.ibd` + redo log / undo log |
| 速度 | 极快（内存 + O(1) 级操作） | 相对慢（B+ 树 + 磁盘 IO） |
| 数据模型 | key-value（string / hash / list / set / zset） | 表 / 行 / 列，SQL、事务、外键、复杂查询 |
| 典型用途 | 缓存、会话、计数器、**分布式锁**、限流、排行榜 | 业务主数据、需要事务与复杂查询的场景 |
| 容量 | 受**内存**限制 | 受**磁盘**限制 |

**本项目**：Redis 只做**缓存 + 幂等锁**；
业务数据实际落在 **Neo4j（图数据库）** 与 **Milvus（向量数据库）**。

### 8. Transformer 的架构

**整体**：Encoder / Decoder 堆叠（原论文），现在常见三种变体：

- **Encoder-only**：BERT —— 理解类任务（分类、抽取）；
- **Decoder-only**：GPT / DeepSeek —— 生成类任务（当前主流）；
- **Encoder-Decoder**：T5 / 翻译 —— 序列到序列。

**每一层的两个核心子模块：**

1. **多头自注意力（Multi-Head Self-Attention）**
   `Attention(Q,K,V) = softmax(QKᵀ / √d) · V`
   让每个 token 直接关注序列中**所有** token（长距离依赖，且可并行）；
   多头 = 在不同子空间学不同的关注模式；
2. **前馈网络（FFN）**：逐位置的两层 MLP + 激活，提供非线性变换能力。

**配套组件：**

- **位置编码**（正弦 / 可学习 / **RoPE**）—— 因为注意力本身**不感知顺序**；
- **残差连接 + LayerNorm** —— 训练深层网络的稳定器；
- **Mask** —— Decoder 用**因果掩码**防止"看到未来"。

**为什么强**：**并行计算**（不像 RNN 必须顺序）+ **全局依赖**（任意两 token 直连，路径长度 O(1)）。

### 9. 切片策略有哪些

| 策略 | 做法 | 特点 |
|---|---|---|
| **固定长度** | 按字符/token 数硬切 | 简单，易切断语义 |
| **递归切分**（**本项目使用**） | 按分隔符**优先级递归**尝试（段落 → 换行 → 句号 → 逗号 → 字符） | 尽量落在语义边界，通用性好 |
| **语义切片** | 相邻句 embedding 相似度骤降处切 | 质量高，成本高 |
| **结构化切片** | 按文档结构（Markdown 标题、PDF 页、表格行） | 结构清晰时最准 |
| **父子切片（small-to-big）** | 小块检索、大块喂 LLM | 兼顾检索精度与上下文完整 |

**参数**：`chunk_size` + `chunk_overlap`（本项目 **600 / 100**，约 1/6 重叠防语义截断）。

### 10. SFT 是什么意思

**SFT = Supervised Fine-Tuning，有监督微调。**

- **做法**：用**标注好的（输入，期望输出）样本对**，继续训练预训练模型；
- **目的**：让模型**学会遵循指令**、适配特定领域/风格（而不只是"会说话"）；
- **与其他阶段的关系**：
  **预训练**（学语言与知识）→ **SFT**（学听指令）→ **RLHF / DPO**（学人类偏好对齐）；
- **成本**：全参微调昂贵；常见轻量方案是 **LoRA / QLoRA**（冻结基座，只训练低秩适配器）。

> 呼应文末简历：那里用的正是 **QLoRA（4bit NF4 + rank=16 低秩适配器）** 做领域适配。

5、设计**独立第二次 LLM 调用**的事实护栏（规避"自检偏见"），无依据时在答案末尾追加"请谨慎参考"提醒并 fail-open 降级，兼顾医疗场景的可用性与责任边界；整体按 **Clean Architecture（端口-适配器）** 分层，用 AST 静态测试固化依赖方向，**147 个测试用例全离线**（零数据库/网络依赖，无 Docker 亦可回归）。
