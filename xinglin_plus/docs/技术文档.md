## 2. 核心数据流

### 2.1 `hybrid` 模式（默认）

```text
用户问题
   ↓
[1] 双路召回
    ├─ 图谱召回 _graph_recall()：NL2Cypher.answer() → LLM 生成 Cypher
    │                          → 规则 + EXPLAIN 校验 → 执行 → 格式化
    │                          失败则降级为空，不阻塞
    └─ 向量召回 RAGAgent.recall()：Milvus 检索 → 拼接带「来源 + 页码」的上下文
   ↓
[2] 融合生成：DeepSeek 结合 <graph_facts> 与 <context> 两路信息生成中文回答
   ↓
[3] 事实护栏 _guard()：第二次 LLM 调用核查答案是否有据可依
                        无依据 → 在答案末尾追加「请谨慎参考」提醒
   ↓
输出
```

### 2.2 `agent` 模式（工具编排，ReAct）

不是固定流水线，而是 ReAct 循环（LangGraph `create_react_agent`，步数上限 10）：

```text
用户问题
   ↓
[1] LLM 自主决策：调 graph_search（图谱结构化事实，上限 20 条）
                  或 literature_search_tool（双路检索片段，上限 8 条）
   ↓  观察工具结果 → 继续决策（可多次、可换工具）
[2] 工具证据经**收集器**回填（图谱事实 / 文献片段分别入桶）
   ↓
[3] 汇总结论 → 来源标识 → 事实护栏（上下文由收集到的证据拼成）→ 依据分级
   ↓
输出
```

**工具失败的降级取向**：工具**不抛异常**，查不到时返回一句可读的观察结果
（如「未检索到相关片段」）。这样失败变成"一条观察"，模型据此可以**自主换用另一个工具**，
或如实承认查不到，而不是让整次问答中断。真正会中断流程的异常（超步数 / 模型异常 /
空回答）由外层兜底：**回落自动问答链路**，保证不空手而归。

`agent` 模式的定位：简单问题不再依赖固定的召回组合；多跳问题
（先查图谱、再据结果决定查哪篇文献）由模型自己编排。

## 3. 自动选路（FR-024）与备用处理（FR-026）

`HybridAgent._route` 的优先级：

```text
开放式问题（进展 / 因果 / 对比）→ 有实体：hybrid 双路 ｜ 无实体：rag 文献
可枚举的信息需求（命中固定类型或有实体）→ kg 结构化知识
寒暄 / 常识（无实体、无类型、非开放式）→ direct 不检索
```

**开放程度优先于"命中了哪一类"**：像"2型糖尿病的药物治疗有哪些新进展"，
虽然沾了"药物治疗"的边（关键词表会命中），但它问的是研究进展，模板答不了，
必须去查文献——否则会出现"有相关文献却回一句资料未收录"。

`open_ended` 由两处共同判定：LLM 的 `open_ended` 字段，以及
`domain/rules/openness.py` 的开放信号词（收窄到真正指向"研究 / 因果 / 比较"的词）。

**FR-026**：`needs_retry()` 只在**依据不足（reliability = low）**时换通路（最多 2 次，`direct` 不参与）。

## 4. 事实护栏（`domain/guardrail/fact_guardrail.py`）

生成之后**用 LLM 做第二次调用**，核查答案中的关键医学陈述是否都能在参考上下文中找到依据。

```python
class FactGuardrail:
    def __init__(self, llm: LLM): ...
    def check(self, answer: str, context: str) -> dict:
        # → {"grounded": bool, "unsupported": [...], "reason": str, "raw": str}
```

| 设计点 | 口径 |
|---|---|
| **为什么要第二次调用** | 避免**自检偏见**：同一轮里既当答题者又当裁判时，模型倾向为已写出的答案辩护。分开调用后，它面对的是"一段声明 + 一段证据"的干净任务 |
| **降级放行（fail-open）** | 无上下文、JSON 解析失败、LLM 异常 → 一律 `grounded=True`，**绝不阻塞问答** |
| **提醒不拦截** | 无依据时用 `add_unsupported_note()` 在答案末尾追加「（提醒：以上回答中部分内容（xxx）在当前知识库中未找到直接依据，请谨慎参考。）」——医疗场景下的责任边界选择 |
| **可关闭** | `HybridAgent(enable_guardrail=False)` / `ToolCallingAgent(enable_guardrail=False)` / `GUARDRAIL_ENABLED=false` |

**所有对话链路共用同一份实现**（单一出口）：证据上下文的拼接（`build_context`）与
「核查 + 追加提醒」（`guard_answer`）都收敛在 `domain/guardrail`，自动问答链路与工具编排
链路都调用它。护栏是"答案级"的最后一道关，与生成方式无关，因此任何新增链路都必须
经过这个出口——`tests/test_guardrail_shared.py` 守住这一点，防止再出现"某条链路绕过核查"。

## 5. 图谱通路：主路径 + 兜底

`NL2CypherAgent` 按顺序取证据，前一层拿不到才走下一层：

```text
① 模板精确查询（QAType 元数据）      零 LLM、结果确定
   └─ 查空 ─▶ ② NL2Cypher（LLM 生成 Cypher + 规则/EXPLAIN 双校验）
                └─ 仍空 ─▶ ③ 规则兜底链（fallback/：词典 + 规则拼 Cypher，零 LLM）
```

第 ③ 层是"大模型挂了，图谱能力不挂"的保证：它完全不调用 LLM。

**安全约束**：Cypher 一律参数化（`$entity`）、走只读会话；`validators.py` 依次做五项检查
——非空 → 只读起始关键字 → 写操作黑名单 → 单语句（禁分号）→ 标签/关系/属性白名单，
再用 `EXPLAIN` 做服务端预检；**模板与生成的语句都强制结果上限**（模板 20 条，
`ensure_limit` 兜底）；LLM 生成的语句**只进日志**，不进入用户可见响应。

## 7. 缓存（`--cache`，可选）

`cli.py` 经**应用层**取用缓存（接口层不直接触碰基础设施）：由组合根提供缓存服务实例，
问答前后分别做读取与写入；缓存不可用时读写各自静默降级（读返回未命中、写空操作），
问答照常。

`infrastructure/cache.py` 覆盖缓存三件套：**穿透**（负缓存）、**击穿**（SETNX 幂等锁）、
**雪崩**（TTL）。Redis 不可用时 `available=False`，问答照常（只是没了秒回）。

排查异常时注意：**缓存里可能留着改代码之前的结果**，清一次即可——

```bat
docker exec xinglin-redis redis-cli FLUSHDB
```

## 10. 效果评测与消融（`evals/`）

`tests/` 管"**逻辑对不对**"（离线、可进 CI）；`evals/` 管"**效果好不好**"
（真机跑，依赖图谱 / 向量库 / 模型服务）。两者**刻意分开**，避免"要联网才能跑单测"。

| 脚本 | 作用 |
|---|---|
| `run_eval.py` | 分层效果评测：固定问答 / 开放式 / 边界 / 安全 → 通过率、工具命中率、时延、护栏触发 |
| `degradation.py` | 依赖逐一失效的容错验证（图谱 / 向量库 / 模型 Key / 缓存 / 护栏超时 / 护栏返回乱码） |
| `ablation.py` | 检索消融（双路 / 仅稠密 / 仅稀疏）、融合权重扫参、护栏混淆矩阵、图谱消融 |
| `performance.py` | 时延构成、并发阶梯（1 / 5 / 10 / 20）、两种编排方式的时延对比 |

**评测集**（`evals/dataset/`）：固定问答 160（从图谱**自动生成**）、开放式 57、
语义改写 19、边界 16、安全 12。生成脚本自带**语料覆盖自检**，题目涉及的文献若不在
语料里会直接报出来（否则测的其实是"拒答能力"而不是"回答能力"）。

**关键设计——真值必须独立**：评测集的真值查询**手写在生成脚本里**，不调用生产的模板
查询实现。否则实现把关系名写错时（本项目就发生过：图谱里叫 `acompany_with`，
代码写成 `accompany_with`），真值会跟着一起错，评测永远"通过"。

**实测结论**（历次报告在 `evals/reports/`）：

| 实验 | 结论 |
|---|---|
| 图谱消融 | 自动编排 **90%** vs 强制纯文献 **0%**——可枚举的问题必须走结构化知识 |
| 融合权重扫参 | 原默认 `0.6/0.4` 让融合**退化为仅稠密**（与单路逐位相同）；改 `0.5/0.5` 后要点覆盖率 92.1% → **97.4%** |
| 检索耗时 | 单次检索 **0.048s**——瓶颈不在检索，而在外部模型调用 |
| 并发阶梯 | 1 → 20 并发**零错误**，P50 稳定 5~6s，瓶颈在外部模型服务 |
| 依赖容错 | 6 个依赖失效场景 **6/6** 通过，且如实反映能力下降 |
| 时延长尾 | 一次性初始化（分词 / 向量模型 / 关键词索引）约 20 秒，出现在**首次**请求；应在启动时预热 |

## 11. 前端

`frontend/index.html` 是**单文件对话界面**（零依赖、零构建），由 `interfaces/web.py`
托管在 `/`，展示最终 Agent 的问答结果。

| 区域 | 内容 |
|---|---|
| 顶栏 | 品牌 + **依赖状态胶囊**（30 秒轮询 `/health`，异常时直接列出挂掉的依赖）+ **深浅色切换按钮** |
| 输入区 | 多行输入、字数计数（上限 500）、示例问题 chips、提问按钮（带加载态） |
| 结果卡片 | 状态提示条（依据不足 / 服务不可用 / 被拒绝）、可靠性 + 检索模式标签、回答正文、健康风险提示、**来源依据**（可折叠：知识图谱 / 医学文献 分别成条）、复制回答 |
| 底部 | 固定免责声明 |

**深浅色主题**：

- 用 CSS 变量 + `html[data-theme="light"]` 覆盖一套取值，配色整体反转（深蓝黑 ↔ 浅灰白）；
- 顶栏按钮一点即在 `dark` / `light` 间切换，选择写入 `localStorage` 持久化；
- `<head>` 里有一段内联脚本**在首屏渲染前**应用主题，避免刷新时闪白/闪黑；
- 首次访问跟随系统偏好（`prefers-color-scheme`）。

**接口**：`POST /v1/chat`（问答）、`GET /health`（探活）。
页面也可直接双击打开——此时 `API_BASE` 自动指向 `http://127.0.0.1:8000`。
